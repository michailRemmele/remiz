Adding a component to a game normally means writing the class, importing it somewhere,
adding it to an array the engine receives, and separately telling the editor it exists.
Four steps. Three of them are clerical, and each one is easy to forget.

The convention on this page removes all of them. A file with the right name is collected
into the game automatically, and the decorator on the class registers it with the editor.

<AutoRegistration />

## Nothing here is built into the engine

The engine takes arrays of classes. It has no glob, no file scanner, and no knowledge of
your directory layout. What collects the files is your project's own entry point, in a few
lines you can read and change.

The editor is no different. It compiles your project with its own bundler, driven by
regular expressions you can edit. It imports every file that matches, and the decorator inside
the file registers the class as it runs.

So what follows is a convention, not a feature. It is worth keeping because the editor's
script generation writes files that follow it, but it is yours.

## The naming convention

Two things make a file part of your project.

**Its name ends with a known suffix:**

| Suffix | Declares |
| --- | --- |
| `*.component.ts` | A component |
| `*.system.ts` | A system |
| `*.behavior.ts` | A behavior |
| `*.shader.ts` | A shader |
| `*.filter-effect.ts` | A filter effect |
| `*.asset.ts` | An asset kind |
| `*.widget.tsx` | An inspector widget |

The editor configuration holds these patterns in five settings, and you can change every one
of them. Shaders and filter effects share a setting with behaviors, because the editor treats
all three as behavior-like classes. The widget setting also matches `.ts`, `.js` and `.jsx`.

Your game's entry point keeps its own list. The
[starter project](/getting-started/installation/) globs components, systems and behaviors,
because that is what most games use. The rest are collected the same way when you need them:
one more glob, written like the three that are already there.

The widget is the one file that never reaches the game. It draws a component's fields in
the inspector, so it is editor code. See [custom widgets](/game-code/custom-widgets/).

**The class is the default export:**

```ts
export default class Health extends Component { /* … */ }
```

A file named `health.ts` is not collected at all. A named export is worse, because the two
sides disagree. The editor imports the file and the decorator registers the class, so the
component appears in the inspector. Your game's glob reads the default export, finds nothing,
and the class never reaches the engine. There is no build error in either case. A widget file
is the exception. It registers itself when it is imported and needs no export at all.

## Two files found by their path

Two parts of a project are located by path rather than by suffix:

| Path | Holds |
| --- | --- |
| `src/events/index.ts` | [Your event names](/concepts/events/#telling-the-editor-about-your-events), so the editor can offer them where an event has to be chosen |
| `src/locales/index.ts` | [Translations for your field titles](/game-code/inspector-fields/#titles-come-from-translations) |

Both paths are settings in the [editor configuration](/editor/config-reference/), like every
pattern in the table above.

## Collecting the files

Here is how the starter project does it. It uses Vite, so it globs with
`import.meta.glob`:

```ts
const gameComponents = importAll(
  import.meta.glob('./**/*.component.ts', { eager: true }),
) as ComponentConstructor[];
const gameSystems = importAll(
  import.meta.glob('./**/*.system.ts', { eager: true }),
) as SystemConstructor[];
const gameBehaviors = importAll(
  import.meta.glob('./**/*.behavior.ts', { eager: true }),
) as BehaviorConstructor[];
```

`importAll` is two lines and lives in your project, not in the engine:

```ts
export const importAll = (modules: Record<string, unknown>): unknown[] =>
  Object.values(modules).map(
    (module) => (module as Record<string, unknown>).default,
  );
```

The pattern has to be a literal at the call site. Vite rewrites `import.meta.glob` at build
time, so it cannot come from a variable or be wrapped in a helper of your own.

On another bundler the shape of this code changes, and only this code. With webpack the
equivalent is `require.context('./', true, /\.component\.ts$/)`, and `importAll` takes a
`__WebpackModuleApi.RequireContext` instead. That also means adding `@types/webpack-env` to
your dev dependencies, or TypeScript will not know the symbol.

## Handing them to the engine

The collected arrays are spread in alongside the built-ins:

```ts
const engine = new Engine({
  config,
  systems: [Renderer, PhysicsSystem, BehaviorSystem, ...gameSystems],
  components: [Transform, Sprite, Behaviors, ...gameComponents],
  assets: [Texture],
  resources: {
    [BehaviorSystem.systemName]: [...gameBehaviors],
  },
});
```

Behaviors are not systems or components, so they arrive as a resource for the behavior
system rather than in either array. Shaders and filter effects work the same way, keyed to
the renderer instead:

```ts
resources: {
  [BehaviorSystem.systemName]: [...gameBehaviors],
  [Renderer.systemName]: {
    shaders: [...gameShaders],
    filterEffects: [...gameFilterEffects],
  },
},
```

:::caution
Being collected is not the same as running. The glob makes a system **available**, and it runs
only if `systems` in `data/data.json` also lists it. The order of that list decides the order
systems run in. See [being collected is not the same as
running](/getting-started/project-structure/#being-collected-is-not-the-same-as-running) for
how components and behaviors differ here.
:::

From the engine's point of view nothing unusual happened. It received arrays of classes,
exactly as it would have if you had listed them by hand.

A name in the configuration with no class behind it fails differently for each kind. A
missing system is dropped, and so is a missing behavior. Both write a line to the console,
`System not found: …` or `Behavior not found: …`, and the rest of the game runs. A missing
component is not handled. The engine tries to construct a class it does not have, and building
the actor fails. So a renamed component file breaks the scene rather than leaving a gap in it.

## What the decorators cost your game

Nothing at run time. Outside the editor, `@DefineComponent` sets the static name on the
class and returns, and `@DefineField` does nothing at all. The field and widget metadata is
built only when the editor is the thing importing the class, which the decorators check for
as they run.

## The round trip

The payoff is the loop between the editor and your project.

Generate a component from the editor. It writes `health.component.ts` into your project.
Two independent things then happen without you doing anything:

- **Your game** picks it up on the next rebuild, because the glob matches the filename.
- **The editor** picks it up by reading the file and finding the decorator, which registers
  the class and its fields into the inspector.

The component becomes placeable on actors and its fields become editable, in the same
session, from a class that did not exist a minute ago.
