## The configuration is the game

Everything the engine needs to build a world is description: the scenes, the actors in
them, the components on those actors and their values, the templates, and the systems with
their options. Here is a scene with a single actor in it, abridged — the shape of what the
editor produces:

```json
{
  "startSceneId": "b8f1…",
  "scenes": [
    {
      "id": "b8f1…",
      "name": "island-level",
      "actors": [
        {
          "id": "4",
          "name": "background",
          "children": [],
          "components": [
            {
              "name": "Transform",
              "config": {
                "offset": { "x": 0, "y": 0 },
                "rotation": 0,
                "scale": { "x": 1, "y": 1 }
              }
            },
            {
              "name": "Sprite",
              "config": {
                "src": "assets/terrain/grass.png",
                "width": 320,
                "height": 320,
                "fit": "repeat",
                "sortingLayer": "terrain"
              }
            }
          ]
        }
      ]
    }
  ],
  "systems": [
    {
      "name": "Renderer",
      "options": { "windowNodeId": "root", "backgroundColor": "#000" }
    }
  ]
}
```

Two things are worth noticing. Components and systems are referred to **by name** —
`"Transform"` is a string, not an import. And there is no logic anywhere: the file says
what exists, never what happens.

## Your game builds the engine

Because the configuration names classes as strings, the engine has to be handed the actual
classes to match those names against:

```ts
import { Engine, Renderer, Transform, Sprite, Texture } from 'dacha';

import config from '../data/data.json';

const engine = new Engine({
  config,
  systems: [Renderer],
  components: [Transform, Sprite],
  assets: [Texture],
});

void engine.play();
```

That is the entire entry point. `config` is imported like any other module, so a save in
the editor reaches the running game through your dev server.

:::caution
The lists have to cover everything the configuration refers to. A scene using `Sprite`
needs `Sprite` in `components`, `Renderer` in `systems` and `Texture` in `assets`, or
`play()` throws at startup instead of quietly rendering nothing.
:::

## Inside a frame

Once the world is built, the loop takes over. It runs on `requestAnimationFrame` and calls
systems in two separate phases.

<FrameDiagram />

**`update`** runs once per rendered frame and receives a variable time delta.
**`fixedUpdate`** runs on its own clock, at a rate that does not follow the frame rate; in
one frame it may run several times, once, or not at all.

The split exists so that a game behaves the same on a 60 Hz laptop and a 144 Hz monitor.
When you write a system you choose the phase: movement, physics and gameplay timers go in
`fixedUpdate`; input, cameras, animation and anything that should track the display go in
`update`.

:::tip
The renderer is a system like any other, running in `update`. There is no privileged render
stage, and nothing stops you from adding a system that runs after it.
:::

## Systems act on actors

A system receives its scene and works with the actors in it. This is what the editor
generates when you create a new system, with the body filled in:

```ts
import { SceneSystem, Transform } from 'dacha';
import type { Scene, Time, SceneSystemOptions } from 'dacha';

export default class SpinSystem extends SceneSystem {
  private scene: Scene;
  private time: Time;

  constructor(options: SceneSystemOptions) {
    super();

    this.scene = options.scene;
    this.time = options.time;
  }

  update(): void {
    const { deltaTime } = this.time;

    for (const actor of this.scene.children) {
      const transform = actor.getComponent(Transform);
      transform.local.rotation += deltaTime * Math.PI;
    }
  }
}
```

`deltaTime` is in seconds, so that is half a turn per second regardless of frame rate.

Iterating the scene directly is fine, and for a small system it is the clearest thing to
do. When a system needs "every actor that has these components", including ones spawned
later, `ActorQuery` does that bookkeeping for you — see
[systems](/concepts/systems/).

## The editor reads the same project

The editor learns about your components and systems by scanning your source for files
matching a set of patterns, importing them, and letting the decorators on each class
register it along with the fields the inspector should draw. It reads your assets directory
the same way.
